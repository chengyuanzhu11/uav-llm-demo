# UAV + LLM：一个月首稿路线建议

日期：2026-10-04。约束：单人推进、一个月首稿、无导师方向限制、主要依赖 API，GPU 只能租用消费级资源。

## 1. 结论

**推荐暂停扩充自研仿真的功能，把 MultiUAV-Plat / Agent4Drone 作为首选复现对象；先诊断任务完成判定失败，再决定是否研究“带来源与时效的执行证据绑定及局部修复”。**

这不是已经确认的新颖方法，而是有论文结果和代码线索支持、适合一周内证伪的候选研究问题。一个月的合理目标是“有可复现实验的完整首稿”，不能保证论文被接收，也不能提前确定投稿档次。

自己写代码不是论文的障碍。当前欠缺的是：一个与已有方法可区分的问题、足够强且公平的 baseline、能隔离贡献的实验，而不是更多建筑、鸟形、按钮或飞控接口。

阅读范围：指定目录的 23 份 PDF 已做首轮定位；重点核对任务规划、反馈修复、导航完成判定论文的方法与实验。不是 23 篇逐段精读。逐篇范围、证据和限制见 [论文证据表](<C:/Users/kyrie/Documents/New project 3/reading-notes/2026-10-04-uav-llm-paper-evidence.md>)。公开仓库检查不等于运行复现。

## 2. 为什么当前项目难以证明 LLM 的价值

以下来自当前代码，而不是旧聊天印象：

- [mission_service.py](<C:/Users/kyrie/Documents/New project 3/uav_llm_demo/mission_service.py:66>) 的默认任务仍是从当前位置安全飞到目标区域。已知坐标和几何障碍的点到点任务，本来就是传统规划器擅长的领域。
- [agents.py](<C:/Users/kyrie/Documents/New project 3/uav_llm_demo/agents.py:175>) 的 Mock 是实际的几何搜索规划器，不是随机弱基线。Mock 表现好是合理现象，不能靠削弱它来制造 LLM 优势。
- [mission_service.py](<C:/Users/kyrie/Documents/New project 3/uav_llm_demo/mission_service.py:264>) 在 DeepSeek 路线反复不合法后可采用本地安全路线；执行中还会安全重接后续 waypoint。最终成功由混合系统共同完成，不能全部归因于 LLM。
- [avoidance.py](<C:/Users/kyrie/Documents/New project 3/uav_llm_demo/avoidance.py:16>) 当前使用观测速度的短时预测，已不是旧的未来轨迹查询。但这些观测仍来自仿真，不能据此声称验证了真实视觉感知或真实鸟类避障。
- [benchmark.py](<C:/Users/kyrie/Documents/New project 3/uav_llm_demo/benchmark.py:11>) 当前按场景固定种子运行，虚拟控制时钟与异步规划线程并存，每轮仅等待 0.001 秒。它适合回归检查，不宜直接作为 Mock/API 真实时延或大规模统计比较的论文协议。

应将 LLM 的作用放在：语言任务理解、目标消歧、多条件任务分解、部分观测下的信息获取和失败后的任务修复。局部避障、轨迹和飞控继续使用确定性算法。

## 3. 为什么优先 MultiUAV-Plat

### 3.1 直接的实验线索

本地 [MultiUAV-Plat PDF](<C:/Users/kyrie/Desktop/paper/UAV&LLM/15_Zhang_2026_MultiUAV_Plat.pdf>) 第 10 页表 4：相同 deepseek-v4-pro 下，ReAct 的任务通过率为 63.60%，Agent4Drone 为 70.27%，相差 6.67 个百分点。这里不能拿不同模型的结果作方法增益。

第 11 页表 6 更值得研究：

| 验证条件 | 检查数 | ReAct | Agent4Drone |
|---|---:|---:|---:|
| 指定方向移动距离 | 1917 | 77.99% | 98.85% |
| 由指定无人机到达目标 | 1049 | 66.35% | 65.40% |
| 目标已到达 | 317 | 93.38% | 84.54% |
| 任务进度 | 83 | 77.11% | 50.60% |

解释边界：这说明“动作执行改善不必然带来完成条件改善”，**不能仅凭汇总表断言原因就是旧记忆或无人机绑定错误**。任务进度一项只有 83 次检查，尤其不能过度推广。作者也将目标定位、最终条件核验和过早完成声明列为后续问题。

### 3.2 可复现条件

[官方仓库](https://github.com/zhangsheng93/MultiUAV-Plat) 可见 server、Agent4Drone、评测数据目录和可选可视化；[benchmark 目录](https://github.com/zhangsheng93/MultiUAV-Plat/tree/main/benchmark) 有 benchmark.zip。论文给出 75 个会话、1500 项任务、9396 项隐藏检查。主要是结构化工具交互，不要求先训练 VLA 或重建 UE 场景。

已确认“代码与数据入口存在”，**尚未解包数据、安装依赖、执行任务或复现论文数值**。第一阶段必须确认 runner、ReAct 对照实现、模型配置、公开代码与论文版本是否一致，不能将当前 main 自动等同于论文提交版本。

选多机平台并不意味着把你的单机项目改造成多机系统：直接复用现有平台的多机机制，只改一个 agent 层模块，避免自己重写通信、分配和仿真。

### 3.3 代码层线索及反证

[blackboard.py](https://github.com/zhangsheng93/MultiUAV-Plat/blob/main/agent4drone/blackboard.py) 的 `ingest_nearby()` 接受观察者和观察步，`_ingest_entities()` 也接收它们，但当前写入实体记录时未保存这两个字段（原文件约 138–174 行）；`compact_entry()` 主要输出最新实体事实。这是“来源/时效是否丢失”的可检验线索，不是已证实的运行失败原因。

另一方面，[system_prompt.py](https://github.com/zhangsheng93/MultiUAV-Plat/blob/main/agent4drone/template/system_prompt.py) 已要求精确 ID 匹配、将 `partial_success` 视为未完成、把黑板看作最后已知而非当前真值。因此不能宣称 baseline 完全没有验证，也不能把重复这些规则写进 prompt 当新贡献。先追踪完整工具返回和执行日志，确定已有路径能否弥补黑板的遗漏。

## 4. 一个候选研究问题

**在相同观测权限、底层工具和调用预算下，显式维护带无人机绑定、目标绑定、来源与有效性的任务证据，是否能减少 LLM 的错误完成判断，并以较少重复执行完成剩余任务？**

暂定题目：*面向部分可观测多无人机任务的执行证据绑定与局部修复*。这是研究范围，不是提前承诺结果的论文标题。

### 4.1 最小方法，而非再搭一个大 Agent 框架

1. **任务条件表示**：由语言生成小型条件集合，如 `visit(drone_A, target_B)`、`photo(drone_A, target_B)`、顺序依赖和覆盖条件；仅来自用户任务与合法 API 定义，不能从隐藏评测器提取答案。
2. **证据记录**：每条记录绑定 task/subgoal、实体 ID、执行者、观察来源、观察步及工具状态。区分“指令收到”“部分执行”“事实已观察”“条件满足”；未知不当作失败或成功。
3. **选择性失效**：区分历史事件与当前状态。曾访问目标不因后来离开而失效；当前位于目标会随移动失效；无人机改派只影响依赖它的条件。不要对所有事实统一设置 TTL。
4. **剩余任务修复**：先廉价查询缺失证据；必要时只让 LLM 修复未满足条件及其依赖，保留仍成立的完成证据。动作层继续调用原有导航与避障工具。

示例：任务要求 A 拍摄目标甲、B 访问目标乙。即使甲已被 B 访问，也不能作为 A 已完成拍摄的证据；A 移动命令部分成功时，不应重做 B 的已完成任务，更不能直接宣布整项完成。

新意若成立，应来自可泛化的条件绑定/失效机制及其因果证据，而不是字段名、图结构、多个 agent 或新缩写。只修复上游代码遗漏，不足以支撑完整方法论文。

### 4.2 已存在的相近工作

- **LLaMAR** 已有 Planner/Actor/Corrector/Verifier 和完成进度维护；**TACOS、CoMuRoS** 已有反馈恢复与重分配。通用验证闭环不是空白。
- **MUTP-LLM** 已有语言转换、HTN、waypoint 和逻辑/物理双层验证。不能以“LLM + 传统规划 + 安全检查”为核心新意。
- 补充检索的 [Neuro-Symbolic Agentic AI for Networked Low-Altitude UAVs](https://arxiv.org/abs/2609.19961) 已讨论完成任务前的显式证据条件；[EAMSR](https://www.mdpi.com/2504-446X/10/9/708) 涉及执行前的证据化任务准入。证据一词本身不新，需要区分运行时归属、事件/状态有效性与局部修复，并继续核对全文。
- [PyRUA-Lean](https://arxiv.org/abs/2610.01939) 已涉及局部条件检查、重试和选择性反馈。不能只用“少调 API”作为独立新意。

补充检索仅是相近工作的定向核查，不是完整系统综述；上述新增论文主要核对摘要/方法概述。**当前不能断言该候选贡献已具备充分新颖性。**

## 5. 必须先做的对照实验

### 5.1 第一周诊断

从 3 个场景族 × 5 个难度各固定抽 1 个完整会话，共 15 会话、300 任务，作为开发诊断集。任务按原顺序运行，不挑选有利例子。

先运行原版 Agent4Drone，再根据成本运行同模型 ReAct。按“观测不足/实体或执行者绑定错误/执行未完成/错误完成判断/导航失败/预算或 API 失败”标注失败，可给一个主因和若干次因；抽样由人检查，不只让同一个 LLM 自评。

关注两类反例：即使新方法也缺少合法证据的不可判定情况，以及原方法已经通过工具反馈正确处理的情况。若本地现象与表 6 不一致，先查版本、模型、协议，不编造支持假设的解释。

### 5.2 主对照控制在五组

| 组别 | 用途 | 必须相同的部分 |
|---|---|---|
| ReAct | 通用闭环参照 | 模型、工具权限、任务、预算 |
| 原版 Agent4Drone | 主要 baseline | 完整原有导航/覆盖/感知工具 |
| Agent4Drone + 提示检查表 | 排除只是 prompt 不够明确 | 条件内容不比新方法少 |
| Agent4Drone + 简单规则状态机 | 排除只是加了常规工程检查 | 可用传感状态与工具返回一致 |
| 候选证据绑定与局部修复 | 检验研究假设 | 不获得隐藏状态或额外 oracle |

传统 CBBA 不直接接收自由语言。只有研究任务分配时才在相同已解析任务上比较 CBBA/MILP，不能把它们与完整语言 Agent 的总成功率混在一起。当前项目的 Mock 也不是多条件语义任务的充分 baseline。

消融优先三项：去掉执行者/目标绑定；去掉事件/状态失效区分；改为全任务重规划。先在开发集验证机制，再将预先选定的关键消融用于保留集，不根据保留集结果不断改规则。

### 5.3 数据与统计协议

- 保留原始完整 75 会话任务顺序。论文协议在任务之间重置电量并降落，但保留最终位置；不能逐任务回到初始坐标后仍称同一协议。
- 15 会话用于开发，余下 60 会话作为预先锁定的保留集；报告全套结果时明确哪些任务参与了开发。另按任务模板留出做泛化诊断，样本不足则如实限制结论，不强称跨模板泛化。
- 主指标为隐藏评测器的严格任务通过率。辅助报告错误完成声明率、正确完成却未声明的遗漏率、各条件通过率、重复动作、调用/tokens/费用和墙钟时间；定义分母并记录零声明情形。
- 任务在会话内相互依赖，置信区间应按会话聚类重采样，不把每个检查或 1500 个任务都当独立样本。主比较采用相同会话配对，记录多次 LLM 重复运行的波动。
- 目标是主方法与主 baseline 至少 3 次配对重复；其他对照根据实测预算安排并公开次数。所有尝试计费、超时和失败都纳入，不只比较双方成功的样本。固定模型标识、推理设置、最大 tokens、工具/LLM 调用上限、超时和代码版本。

隐藏检查可用于离线评分；运行时只能使用原 baseline 可访问的验证反馈，禁止通过 ADMIN 角色、评测 JSON 或全局真值绕过部分可观测性。

## 6. 四周计划与止损点

| 时间 | 实际交付 | 不满足时怎么办 |
|---|---|---|
| 第 1–3 天 | 独立目录复现最小会话；确认 ReAct、Agent4Drone、数据版本、权限与评分；测真实费用 | 三天仍无法闭环，不继续无限修环境；评估下述备选 |
| 第 4–7 天 | 300 任务诊断、失败分类、简单检查表/状态机对照、小型干预实验 | 若目标机制很少出现，或简单规则已消除差距，不做该方法选题 |
| 第 8–14 天 | 冻结问题和算法，完成单模块实现与开发集消融；同步写方法/实验协议 | 新增模块不能解释收益则删去；不扩为完整新框架 |
| 第 15–23 天 | 保留集主对照、关键消融、配对重复和失败分析，生成图表 | 算力/费用不足则缩小声明范围并公开子集，不伪称全 benchmark |
| 第 24–30 天 | 完整首稿、相关工作差异表、复现实验说明与自审 | 负结果如实写成诊断/评测结论，不伪造方法增益 |

第七天继续条件：能复现协议；目标失败在多个模板/会话出现；合法观测足以支持修复；小型干预显示值得扩大实验的改善趋势，且不是简单提示增强就同样解决。趋势不是显著性证明，最终由保留集决定。

首稿推荐四幅核心图/表：方法及信息权限图、主结果表、收益/回归的配对失败分类图、成功率与调用成本的权衡及消融。不要把城市效果图当主要实验证据。

## 7. 资源、费用与备选

首选路线先用 API，不要求租 GPU 训练大模型；本机运行结构化仿真。可视化不是批量评测的必要条件。消费级 GPU 可以后续补一个开源小模型实验，但不是首稿关键路径，不能提前假设所有模型都能单卡部署。

MultiUAV-Plat 本地论文第 10 页报告一次 deepseek-v4-pro 全套运行约 400 元、超过 3.5 万次请求。这是作者当时的特定配置，不是当前报价或你的预算承诺。先测 pilot 的实际费用和墙钟时间，再按任务量、组数、重复次数估算并设置硬上限；缓存命中波动也要计入。若机械照此历史成本做五组各三次，量级会到约 6000 元，而不是“一套 400 元就够”。这是警示性外推，不是报价。

只保留两个备选：

1. **CityAVOS / PRPSearcher**：若更偏好单机视觉搜索，复现后研究语义先验与探索触发的可靠性。它已有完整搜索与触发机制，不能只加阈值；Windows UE5.3、修改的 AirSim、Grounded-SAM 等依赖使一个月搭建风险较高。[官方代码](https://github.com/jiyatai/CityAVOS)
2. **LLaMAR 的 SAR 环境**：若 UAV 主平台确实难以复现，可用现有多机器人搜救环境验证同一个任务层问题，但论文应明确是机器人任务规划，不能包装成真实 UAV 导航。原模型已变化，要同模型重跑对照。[官方代码](https://github.com/nsidn98/LLaMAR)

DroneCATS 很适合支持失败现象，但此次检查 [官方仓库](https://github.com/naver-ai/DroneCATS) 只有 README，不能把未公开的执行代码当本月可靠起点。RecoverFly 的训练配置为 8 张 A100 80GB、约 21 小时，见本地 PDF 第 5 页；这不是消费级单卡一个月研究的优先路线。LoRA 并不自动意味着整体闭环训练便宜。

## 8. 现有项目如何保留

保留 API 接入、结构化输出、安全检查、连续运动、动态交通、日志和 HTML 可视化，不删除、不重写。将来可用它展示候选方法在连续运动中的表现，但主实验证据优先来自公开平台。

若之后做二次验证，须分开记 LLM 原始方案、拒绝原因、Mock 接管、本地避障接管和最终成功。不要因有本地兜底而宣称 LLM 本身提高了安全性，也不以隐藏鸟类未来轨迹、放宽目标判定或删除困难案例制造结果。

本次未修改仿真业务代码、未重启 Flask、未调用付费 API、未运行第三方 baseline。当前交付是文献证据与研究决策；下一步的具体工作应是**独立复现 MultiUAV-Plat 的一个完整会话，然后执行第一周诊断**。
